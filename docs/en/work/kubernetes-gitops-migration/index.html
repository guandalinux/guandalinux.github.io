Moving an authentication service from virtual machines to Kubernetes with GitOps

I wrote the GitOps repository that moved an authentication service from virtual machines to Kubernetes, with no public cloud provider. A colleague then built a shared platform repository from it and extended it to a new product.

Period
March 2025 to April 2026 (repository built from 8 January to 26 March 2026)
My role
Initiator, later taken over by others

Initiator, later taken over by others. I wrote 214 of the 251 non-merge commits in the GitOps repository and remained its only human author until 31 March 2026.

Context

An authentication service ran on four virtual machines: two in production, two in pre-production. It relied on an external database and on shared sessions. The target was Kubernetes on private infrastructure, with no public cloud provider.

What I did

  1. I opened the project in March 2025 and split it into work packages: infrastructure, application and monitoring, then CI/CD and security in September 2025.
  2. I prototyped a local cluster on 3 virtual machines, then built a pre-production cluster with 3 control-plane nodes and 3 worker nodes.
  3. On 8 January 2026 I created the GitOps repository: 141 files, 13 infrastructure components, three ArgoCD application generators, and a Kustomize base with per-environment overlays.
  4. Without a cloud provider, I set up load balancing through L2 announcements and IP pools in the CNI, ingress through Gateway API with Envoy Gateway (HTTP, HTTPS and TCP), and Longhorn distributed storage.
  5. I handed the cluster's secrets to an external secrets operator backed by a vault, then replaced its token authentication with Kubernetes authentication.
  6. I made data and session access redundant (a 3-replica SQL proxy in front of the external database, Redis Sentinel behind HAProxy) and tuned the application's health probes and rolling updates.
  7. I prepared continuous delivery: the pipeline writes the image tag into Git, ArgoCD deploys, and the CI agent has its own service account with roles limited to two namespaces.
  8. On 10 March 2026 I added the production environment for the platform and the service in a single 99-file commit, then on 17 March switched its production configuration to the final domain name.

Technologies

  • Kubernetes (RKE2)
  • Rancher
  • ArgoCD (ApplicationSets)
  • Kustomize
  • Helm
  • Cilium
  • Gateway API / Envoy Gateway
  • Longhorn
  • Vault
  • External Secrets Operator
  • ProxySQL
  • Redis Sentinel

Diagram

Result

Production was running on Kubernetes before 23 April 2026, and the retirement of the 4 old servers was scheduled.

What happened next

A colleague created and restructured a shared platform repository from my files (130 of the 138 imported files identical to mine), reorganised it by cluster, then extended it to a new product in autumn 2026. We grew it together, with that colleague doing most of the work; 99 of its 212 current files are still identical to the ones I wrote. In July 2026 I connected a fourth cluster to it through 19 overlay files (5 components), without touching the shared bases.
