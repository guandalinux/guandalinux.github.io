Production incidents: from diagnosis to a versioned fix

I handle incidents with the operations team, write them up to a fixed outline and, where I can, finish with a fix written in code. One example: a MySQL cluster whose Ansible role I had written went down during an update, and I turned the cause into code in that same role.

Period
February 2023 to October 2026
My role
One contributor among several

One responder among several in the operations team. I wrote the incident reports and the versioned fixes cited here.

Context

84 incident tickets were assigned to me from 2023 to 2026: 32 in 2023, 21 in 2024, 8 in 2025 and 23 in 2026. They involve APIs, proxies, a CI server and databases. The causes often sit between the application and the infrastructure: system limits, abnormal requests, automatic updates.

What I did

  1. My incident reports follow a fixed outline (summary, timeline, root cause, resolution, preventive action): of the 13 incidents assigned to me in the first half of 2023, I wrote up 11 this way.
  2. On a slow CI server, I found 4,944 open files against a limit of 4,096, raised the limit to 30,000 in the systemd unit, and wrote a diagnostic memo for the team.
  3. On an API with abnormal disk I/O, I found a URL returning more than 140,000 items and made the proxy answer it with a rate-limiting status code.
  4. On an API that kept falling over, I worked with a colleague, using tracing, to identify a paginated call for 100,000 items that exhausted the JVM's memory, then blocked those requests in the load balancer's versioned configuration.
  5. On an API returning 502 errors, with memory at 96% and swap at 99%, I cut the HTTP cache from more than 10 GB to 6 GB, then enabled the database query cache and raised its index buffer to absorb the cache purge.
  6. On a reverse proxy returning 502 errors, I established that it was running out of connections and fixed it in the infrastructure code: persistent upstream connections and a metrics exporter.
  7. In 2026 I wrote the Ansible role for a 3-node MySQL InnoDB cluster, with a custom Python module that creates the cluster or adds a node to it, and a local lab of 3 virtual machines.
  8. In autumn 2026 that cluster went down during an automatic update (a third-party package had taken over the database configuration file); I turned the cause into code in my role: enforced configuration, a node-by-node restart that refuses to proceed if a node is offline, a memory buffer reduced from 2 GB to 1 GB, and a working check mode.

Technologies

  • Linux (systemd)
  • nginx
  • HAProxy
  • Varnish
  • Tomcat
  • MySQL InnoDB Cluster
  • Python
  • Ansible
  • Vagrant
  • Prometheus
  • Datadog

Result

Measured incident by incident: open-file limit raised from 4,096 to 30,000; database CPU down from over 400% to under 200% during the cache purge; instance type change for a saturated proxy with 15 minutes of downtime, followed by a dedicated probe and alert rule.

What happened next

The MySQL role ships with separate inventories (local, pre-production, production) and a documented local lab, so someone else can test it on their own.

Note

The October 2026 fix was written with the help of an AI coding assistant, as the commit states.
