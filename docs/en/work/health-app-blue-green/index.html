A containerised health application on public cloud: blue/green deployments, locked backups, tested restore

On a containerised health application, I described every service in Ansible, replaced the manual blue/green switch with three jobs, and rebuilt the backup chain. I tested the restore: 11 minutes for the file server, 9 minutes 40 for the database.

Period
April 2024 to March 2025; web application firewall in September and October 2026
My role
Initiator, later taken over by others

Initiator, later taken over by others. The application, its images and a first blue/green procedure existed before me. I created the infrastructure repository and wrote 69 of its 139 non-merge commits.

Context

The application runs on Docker Swarm on AWS, and releases relied on manual blue/green switch commands. In late August 2024, a retention change made the backup job resync more than four years of files, which badly slowed the production disks; the service was stopped. The arrival of several thousand users then loaded the main node.

What I did

  1. In April 2024 I created object storage locked against modification and deletion, with an instance role limited to uploading files; regular copying of backups to it went live in September 2024.
  2. In September 2024 I documented the cause of the slowdown and added an Ansible playbook to copy backups, then in March 2025 replaced the old backup service with a full playbook.
  3. After spotting a backup outage that had gone unnoticed, I redeployed the service and added a daily check that backups exist.
  4. On 16 January 2025 I created the infrastructure repository; by mid-March I had described every service in Ansible: reverse proxy, application services, databases, backup, secrets and per-environment configuration.
  5. I replaced the manual switch commands with three jobs (prepare the new colour, switch, clean up the old one) and rewrote the procedure; the first two are also available to developers in pre-production.
  6. I added daily volume snapshots kept for 30 days and wrote the step-by-step restore guide, including the failure encountered after a restore.
  7. I extended monitoring: exporters for the containers, the database and the reverse proxy, a dedicated HTTP probe, and reverse proxy access logs shipped to the central logging platform.
  8. In 2026 I rebuilt the reverse proxy image with a web application firewall: sources pinned by checksum, OWASP rules, detection-only by default, and audit logging turned off so no patient data gets written.

Technologies

  • AWS (EC2, EBS, S3 Object Lock, IAM)
  • Docker Swarm
  • Ansible
  • Jenkins
  • Rundeck
  • nginx
  • ModSecurity / OWASP CRS
  • MongoDB
  • Prometheus
  • cAdvisor

Diagram

Result

Restore tested on 19 March 2025: 11 minutes for the file server, 9 minutes 40 for the database. When several thousand users arrived, CPU load on the main node went from over 95% to under 70% after doubling a second node and moving services onto it, then to under 40% after disabling the web application firewall, identified as the cause.

What happened next

From April 2025 to June 2026, day-to-day operation of the repository was mainly handled by others, with occasional work from me. At the development team's request, I let developers change some development and pre-production settings themselves, with everything else fenced off by a code owners file and an automatic check of the paths changed in each merge request. Blocking mode for the web application firewall was later enabled in development.
