Incidents de production : du diagnostic au correctif versionné

J'interviens sur les incidents avec l'équipe d'exploitation, je les documente selon un plan fixe et je termine, quand je le peux, par un correctif écrit dans le code. Exemple : un cluster MySQL dont j'avais écrit le rôle Ansible est tombé pendant une mise à jour, et j'ai traduit la cause en code dans ce même rôle.

Période
Février 2023 à octobre 2026
Mon rôle
Contributeur parmi d'autres

Intervenant parmi d'autres dans l'équipe d'exploitation. J'ai rédigé les comptes rendus cités ici et écrit les correctifs versionnés cités.

Contexte

84 tickets de type incident m'ont été assignés de 2023 à 2026 : 32 en 2023, 21 en 2024, 8 en 2025 et 23 en 2026. Ils touchent des API, des proxys, un serveur d'intégration continue et des bases de données. Les causes se trouvent souvent entre l'application et l'infrastructure : limites système, requêtes anormales, mise à jour automatique.

Ce que j'ai fait

  1. Mes comptes rendus suivent un plan fixe (résumé, chronologie, cause racine, résolution, mesure préventive) : sur les 13 incidents qui m'ont été assignés au premier semestre 2023, j'en ai rédigé 11 sur ce modèle.
  2. Sur un serveur d'intégration continue ralenti, j'ai relevé 4 944 fichiers ouverts pour une limite de 4 096, porté la limite à 30 000 dans l'unité systemd et écrit un mémo de diagnostic pour l'équipe.
  3. Sur une API aux entrées-sorties anormales, j'ai trouvé une URL qui renvoyait plus de 140 000 éléments et l'ai fait répondre par un code de limitation dans le proxy.
  4. Sur une API qui tombait, j'ai identifié avec un collègue, grâce aux traces, un appel paginé à 100 000 éléments qui épuisait la mémoire de la JVM, puis bloqué ces requêtes dans la configuration versionnée du répartiteur de charge.
  5. Sur une API en erreurs 502, mémoire à 96 % et swap à 99 %, j'ai ramené le cache HTTP de plus de 10 Go à 6 Go, puis activé le cache de requêtes de la base et augmenté son tampon d'index pour absorber le vidage de ce cache.
  6. Sur des erreurs 502 d'un reverse proxy, j'ai établi l'épuisement de ses connexions et corrigé dans le code d'infrastructure : connexions persistantes vers l'amont et exporteur de métriques.
  7. En 2026, j'ai écrit le rôle Ansible d'un cluster MySQL InnoDB à 3 nœuds, avec un module Python maison qui crée le cluster ou y ajoute un nœud, et un laboratoire local de 3 machines virtuelles.
  8. À l'automne 2026, ce cluster est tombé pendant une mise à jour automatique (un paquet tiers avait repris le fichier de configuration de la base) : j'ai traduit la cause dans mon rôle avec une configuration forcée, un redémarrage nœud par nœud qui refuse d'agir si un nœud n'est pas en ligne, un tampon mémoire ramené de 2 Go à 1 Go et un mode vérification utilisable.

Technologies

  • Linux (systemd)
  • nginx
  • HAProxy
  • Varnish
  • Tomcat
  • MySQL InnoDB Cluster
  • Python
  • Ansible
  • Vagrant
  • Prometheus
  • Datadog

Résultat

Mesures incident par incident : limite de fichiers ouverts portée de 4 096 à 30 000 ; processeur de la base passé de plus de 400 % à moins de 200 % pendant le vidage du cache ; changement d'instance d'un proxy saturé avec 15 minutes de coupure, suivi d'une sonde et d'une règle d'alerte dédiées.

Suite et passage de relais

Le rôle MySQL est livré avec des inventaires séparés (local, préproduction, production) et un laboratoire local documenté, pour qu'un tiers puisse le tester seul.

À noter

Le correctif d'octobre 2026 a été écrit avec l'aide d'un assistant de code IA, ce que le commit mentionne.
