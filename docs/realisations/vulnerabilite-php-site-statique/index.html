Répondre à une vulnérabilité PHP : remplacer un CMS par un site statique

Deux sites web tournaient sur un CMS PHP touché par une vulnérabilité ; j'ai reconstruit les serveurs en code puis, quand l'équipe produit a choisi un site statique, retiré PHP et la base de données. Le chantier a été ouvert le 22 et clos le 30 octobre 2026.

Période
Du 22 au 30 octobre 2026
Mon rôle
Seul auteur

Seul auteur des commits du chantier. La décision d'abandonner le CMS revient à l'équipe produit, et la reconstruction suivait les préconisations de sécurité d'un collègue.

Contexte

Deux sites web d'un produit tournaient sur un CMS PHP touché par une vulnérabilité. Un collègue avait rédigé des préconisations de sécurité pour reconstruire à neuf. Le site statique lui-même est fourni par les développeurs du produit.

Ce que j'ai fait

  1. J'ai relevé la configuration des serveurs exposés (système, serveur web, version de PHP, CMS et extensions) et reconstruit à neuf en suivant les préconisations de sécurité.
  2. J'ai configuré par Ansible deux serveurs Debian 13 : SSH par clé uniquement, pare-feu où seul le web est public, bannissement automatique des tentatives SSH, exporteurs de métriques système et processus.
  3. Une première phase a reconduit le CMS sur une version de PHP corrigée ; le jour même, l'équipe produit a choisi un site statique, et j'ai retiré des deux serveurs PHP, l'ancien serveur web et la base de données, après export des contenus et des données.
  4. J'ai écrit le projet Ansible qui héberge le site statique : serveur web, politique de sécurité de contenu, redirections permanentes des anciennes adresses, page de maintenance.
  5. J'ai écrit le playbook qui émet le certificat et le renouvelle automatiquement, renouvellement vérifié à blanc.
  6. J'ai ajouté les deux sites au contrôle d'expiration des certificats, qui alerte 21 jours avant l'échéance, et corrigé la première alerte remontée en retirant un service de messagerie inutile qui échouait au démarrage.
  7. J'ai préparé pour les développeurs une publication sans accès aux serveurs : un job d'intégration continue lance un job d'orchestration qui vérifie la liste des fichiers autorisés avant la copie et contrôle les pages après.

Technologies

  • Ansible
  • Debian 13
  • nginx
  • Let's Encrypt
  • fail2ban
  • Prometheus
  • Jenkins
  • Rundeck
  • DNS

Résultat

La production a basculé vers les nouveaux serveurs le 28 octobre 2026, sans PHP ni base de données. Le chantier a été clos le 30 octobre 2026.

À noter

Les huit commits de ce chantier ont été écrits avec un assistant IA, ce que chacun mentionne ; je les ai validés, signés et joués sur les serveurs.
